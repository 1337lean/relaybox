# Threat model

Relaybox accepts attacker-controlled inbox bodies and headers. Controls include bounded body size and concurrent body reads, bounded response capture, header and HTTP timeouts, constant-time HMAC verification when configured, pre-persistence sensitive-header redaction, atomic deduplication, fixed workers and a bounded queue, capped retries, lifecycle cancellation, and restrictive browser headers. The browser UI uses external assets under a CSP that disallows inline script and style.

The administrative surface (list, detail, replay, SSE, and session creation) requires an operator token. The UI exchanges a bearer token for a domain-separated derived session value in an HttpOnly Strict SameSite cookie. State-changing cookie-authenticated requests require an Origin, and all supplied Origins must match both the request host and expected HTTP/HTTPS scheme. `-secure-cookie` establishes HTTPS as the expected external scheme behind a TLS-terminating proxy. The inbox stays unauthenticated so webhook senders can use it; configure `-secret` to authenticate GitHub-style deliveries. Health probes expose only status.

Replay cannot choose an arbitrary URL. The target is fixed by startup configuration, URL credentials and non-HTTP schemes are rejected, redirects and environment proxies are disabled, and the default dialer blocks loopback, private, link-local, multicast, and unspecified resolved addresses. Disabling proxy inheritance is part of the SSRF boundary: otherwise a proxy could resolve and connect to a blocked destination outside the checked dialer. DNS is resolved at connection time. Hop-by-hop and spoofable proxy/Relaybox identity headers are stripped. `-allow-private-targets` deliberately disables the destination-IP boundary for local development and must not be used with untrusted operators or payload sources.

Relaybox does not terminate TLS, provide tenant isolation, encrypt stored bodies, rotate logs, cap total store growth, or impose a sustained inbox request-rate limit. `RELAYBOX_OPERATOR_TOKEN` and `RELAYBOX_SECRET` avoid secrets in process arguments; protect the process environment and startup logs if relying on generated tokens. A compromised operator can read and replay stored payloads. Filesystem and network access remain part of the trusted computing base.

Delivery is at least once. A crash after a destination processes a request but before Relaybox records completion can repeat it. Delivery IDs and body hashes suppress capture duplicates but are operational idempotency keys, not authorization. Downstream receivers should deduplicate Relaybox request/job IDs.
